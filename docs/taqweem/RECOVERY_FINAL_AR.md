## النتيجة وحدودها

نُفّذت إصلاحات الكود والاختبارات داخل `clinic_dental1` فقط. لم تتغير `.env` أو `.env.example` أو APP_KEY أو إعدادات SMTP أو مفاتيح API. لا توجد Migration جديدة أو تغييرات على قاعدة الفريق، ولا نشر أو طلب توليد مدفوع. لم تُحمّل أوزان نماذج أو PyTorch.

**لم تُحل مشكلة وصول Gmail، ولم يعمل توليد AI الحقيقي.** الأجزاء التي نجحت فعلياً والأجزاء المختبرة بـMock مفصولة أدناه.

## البريد: ما أثبته التشخيص

أُرسلت رسالتان فقط في هذه المرحلة، واحدة لكل فرضية، إلى حساب الاختبار المصرح به سابقاً في قاعدة QA المعزولة:

1. إشعار Laravel الأصلي، مع تتبع الأحداث.
2. نفس مسار الإشعار والرابط الموقّع مع قالب نصي فقط، لعزل أثر HTML.

أثبت التتبع في كل مرة:

- حدث `Registered` مرة واحدة.
- `NotificationSending` لقناة mail مرة واحدة، ثم `MessageSending` و`MessageSent` و`NotificationSent` مرة واحدة لكل منها.
- المستلم مطابق لحساب الاختبار؛ لا يوجد تحويل إلى مستلم آخر.
- ناقل SMTP فعلي، والإشعار متزامن وليس مؤجلاً على Queue.
- رد قبول SMTP مطابق لـ`250 2.0.0 OK`، مع وجود Message-ID.
- الإشعار الأصلي يحتوي HTML ونصاً؛ المقارنة تحتوي نصاً فقط.

أفاد المستخدم أن **كلتا الرسالتين لم تصلا**. فحص قاعدة QA أكد أن الحساب الحقيقي المصرح به ما زال غير مؤكد. لم نضغط رابطاً نيابةً عنه ولم نفعّل الحساب يدوياً.

**السبب الجذري للتسليم الخارجي غير مثبت.** الأدلة تستبعد عدم إطلاق الحدث أو عدم تنفيذ قناة البريد في التجربتين، ولا تدعم اتهام قالب HTML. قبول SMTP لا يثبت الوصول إلى الوارد؛ لا يمكن الجزم بأن السبب فلترة Gmail دون أثر من المزود. لهذا لم نستبدل إشعار التطبيق بتخصيص غير مثبت. قالب `verification-plain.blade.php` يُستخدم فقط داخل تجربة التشخيص، ولا يفعله التطبيق تلقائياً.

المطلوب من صاحب حساب الإرسال: فحص «المرسلة» و«كل البريد» وقواعد التحويل وأي ارتداد، أو سجل التسليم لدى المزود، للرسالتين ذواتي عنوان `Verify Email Address` قرب التوقيتين المسجلين في `output/recovery-evidence/email-traces.json`. لا حاجة لمشاركة كلمة المرور أو رابط التحقق. لم تُحفظ محادثة SMTP الخام أو محتوى الرسالة أو الرابط في التقرير؛ حُفظت العدادات والأعلام فقط. لا مزيد من الإرسال التلقائي.

نجحت مجدداً اختبارات التوقيع والانتهاء والعبث وإعادة الإرسال وحدودها والدخول والخروج وتغيير البريد. رحلة التسجيل عبر المتصفح نجحت باستخدام بريد QA المعزول؛ هذا **ليس** إثباتاً على استلام Gmail.

### ما أُصلح

- كانت استجابة AI الخارجية تُضمَّن في الاستثناء ثم السجل، ما قد يكشف معلومات حساسة. أزيل نص الاستجابة والسياق الخام، وبقي نوع الخطأ/رمز HTTP فقط.
- مُنعت Redirects في طلبات AI حتى لا يُرسل رمز الخدمة إلى وجهة محوّلة. احترم عميل Smile مهلة الإعداد بحد أقصى، دون إعادة تلقائية لطلبات توليد قد تتكرر تكلفتها.
- أضيف تحقق فعلي من الصورة والأبعاد وحد 16 مليون بكسل، والتحقق من أن الناتج PNG حقيقي، وليس مجرد Content-Type مزعوم.
- أصبح غياب GD يفشل قبل طلب التوليد. امتداد GD موجود على الجهاز ويمكن تفعيله لكل أمر بـ`-d extension=gd` دون تغيير `php.ini`.
- أُصلح تنظيف الملفات عند فشل حفظ أحد طرفي المعاينة، وحذف المعاينات التي تسقط من حد الجلسة البالغ عشرة. صفحات النتائج والمعرض ترسل `private, no-store`؛ الصور محمية بملكية الجلسة.
- أصبحت معالجة Python الثقيلة خارج حلقة HTTP، مع قفل يشمل الكاش المشترك لكاشف الوجه والنموذج، ورفض سريع عند الانشغال. أخطاء الكاشف لم تعد تكشف المسارات الداخلية.
- أصبح `/health` يميز خدمة HTTP من جاهزية النموذج ويذكر الحزم الناقصة دون مفاتيح.
- عُزّز parsing في Gemini ضد أشكال استجابة غير صحيحة؛ أُضيفت الوصفة إلى مراجعة الملاحظة بعد أن كانت مستبعدة، مع حدود للأطوال واقتباسات لا بد أن تطابق المصدر. تعليمات الحقول تعامل كبيانات، وليست أوامر.
- بقي اعتماد التقرير بيد الطبيب، مع منع المريض من رؤية المسودة ومنع الطبيب الآخر من اعتمادها. عُرض محتوى المسودة escaped في الاختبار.
- كان رفع الصور القديم يفشل في MySQL لأن `ai_analyses` إلزامي بلا قيمة افتراضية. حُفظت قيمة فارغة تعني عدم وجود تحليل، دون تغيير المخطط. بقي `status=pending` للتوافق وأضيف `processing_available=false` ورسالة صريحة. أضيف منع رفع المريض غير المؤكد والحساب المعطل.
- استُبدل تعطيل Gemini الثابت بخيار صريح `GEMINI_REVIEW_ENABLED` الافتراضي false، وأصبح اسم النموذج قابلاً للضبط دون تغيير الافتراضي. لم تُفعّل خدمة قد تكون مدفوعة تلقائياً لمجرد وجود مفتاح.

صيغة `steps` و`response_format` الحالية متوافقة مع [دليل Google الرسمي لترحيل Interactions](https://aistudio.google.com/docs/interactions-breaking-changes-may-2026). لم يُفترض أن تغيير API هو العطل؛ التغيير هنا لتقوية التحقق من الاستجابة.

## المتطلبات الخارجية الناقصة

- `GEMINI_API_KEY` غير موجود في الإعداد المحمّل، وميزة المراجعة معطلة. يلزم توفير المفتاح بطريقة سرية لعملية التشغيل، وتحديد السماح بالتكلفة قبل اختبار طلب حقيقي. لا ترسله في المحادثة ولا يلزم تعديل ملفات البيئة المحمية لهذه المهمة.
- `MEDASSIST_AI_TOKEN` غير موجود. يلزم توفير الرمز نفسه لعمليتي Laravel وPython عبر إعداد تشغيل آمن.
- أُنشئت Python 3.11 وبيئة `.venv` داخل المشروع وثُبتت حزم HTTP والصور الخفيفة فقط. الحزم الثقيلة الناقصة: Torch وDiffusers وMediaPipe وTransformers وAccelerate وSafetensors.
- لا توجد أوزان SDXL في المشروع أو موقع Hugging Face الافتراضي الذي فُحص. ملف Face Landmarker موجود، لكن لم يُختبر تحميله مع MediaPipe. GPU الموجود بذاكرة 4GB؛ لم تُختبر كفايته. تنزيل الحزم الثقيلة والنماذج يحتاج موافقة منفصلة.
- الكود يستخدم `local_files_only=True`: لا ينزل النموذج تلقائياً. صُحّح README الذي كان يدعي التنزيل عند أول طلب.

## نتائج الاختبارات

- PHPUnit مع GD: **31 اختباراً و217 تحققاً ناجحاً**، دون تخطي.
- PHPUnit بدونه: **31 اختباراً و210 تحققات ناجحة**، بما فيها منع استدعاء AI عند غياب معالجة الصور.
- Python: **7 اختبارات ناجحة**؛ مصادقة، أحجام وصيغ، غياب الكاشف، انشغال النموذج، HTTP، وPipeline وهمي معلن يحافظ على البكسلات خارج القناع.
- خدمة Python الحقيقية: HTTP 200 لحالة `degraded` وHTTP 503 لطلب توليد بلا رمز، دون ادعاء إنتاج صورة.
- المتصفح: **35 تحققاً ناجحاً** لرحلة التسجيل والحجز وتأكيد الطبيب والإدارة واللغة والخروج، دون أخطاء JavaScript. اختبار Smile مستقل أثبت تعطيل الزر عند غياب الخدمة وخطأً واحداً عند تجاوز الواجهة في اختبار سلبي.
- PHP Syntax: 73 ملفاً دون أخطاء؛ نجح Blade compilation وVite production build.
- نجحت اختبارات التقارير مع MySQL معزول وبيانات اصطناعية، وحماية الصور بين الجلسات، وعدم عرض مسودة غير معتمدة. لم تُستخدم بيانات مرضى حقيقية.

ظهر أثناء الاختبارات خطأ الحفظ القديم المذكور وأُصلح. لم تُرصد انتكاسة في الرحلات المختبرة. اختبارات التحميل على GPU وجودة الصورة الطبية والتسليم الخارجي ليست ناجحة أو مكتملة؛ لا تشملها ادعاءات النجاح.

## التشغيل على Windows

خادما QA وPython يعملان حالياً على 8199 و8001. لا تشغّل نسخة ثانية على المنفذ نفسه. بعد إيقاف الخادم السابق، من مجلد المشروع:

```powershell
# QA مع GD، دون تغيير إعدادات PHP العامة
php -d extension=gd -S 127.0.0.1:8199 -t public tools/qa-router.php

# Python للتشخيص فقط، دون تمكين توليد
.\medassist-ai-engine\run.ps1 -Diagnostics

# اختبارات Laravel
php -d extension=gd vendor/bin/phpunit --no-progress
php artisan view:cache
npm.cmd run build -- --configLoader runner

# اختبارات Python
Push-Location medassist-ai-engine
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
Pop-Location
```

بيئة QA تعزل قاعدة البيانات والبريد وخدمات AI عمداً. تشغيلها لا يثبت تفعيل مفاتيح التطبيق الحقيقي. لإكمال الخدمة الفعلية راجع `medassist-ai-engine/README.md` والمتطلبات أعلاه. لا تُعِد تشغيل أدوات إرسال البريد؛ سجّلت التجربتين بالفعل.
